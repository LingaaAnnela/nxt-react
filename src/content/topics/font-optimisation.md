# Font Optimisation — next/font

Loading fonts from an external CDN at runtime is the default web behaviour — and it has significant downsides. `next/font` eliminates them by handling fonts at build time instead.

## The problem with a `<link>` to Google Fonts

```html
<!-- What most sites do: -->
<link rel="stylesheet" href="https://fonts.googleapis.com/css2?family=Inter" />
```

When the browser encounters this tag it must:

1. Resolve the DNS for `fonts.googleapis.com` (extra RTT)
2. Connect to Google's CDN (TLS handshake)
3. Download the CSS file
4. Parse the `@font-face` rules inside it
5. Connect to `fonts.gstatic.com` to download the actual font files
6. Only then render text in the custom font

Every user's browser makes these requests. Google sees every user's IP address. If Google's CDN has a slowdown, your fonts load slowly.

## What next/font does instead

```ts
// src/lib/fonts.ts
import { Inter, Playfair_Display } from 'next/font/google';

export const inter = Inter({
  subsets: ['latin'],
  variable: '--font-inter',
  display: 'swap',
});
```

At `next build`, Next.js:
1. Downloads the font files from Google — once, on your build machine
2. Bundles them into the static output under `/_next/static/media/`
3. Generates a `@font-face` rule pointing to your own origin
4. Generates a **size-adjusted fallback** `@font-face` for the system font

The browser receives font files from your own server, same origin as everything else. No third-party DNS, no third-party TLS, no privacy leak.

## size-adjust — eliminating Cumulative Layout Shift

CLS (Cumulative Layout Shift) happens when the custom font loads after the fallback: letters are wider or taller, elements reflow, the user's reading position jumps. This is a real UX problem and penalises Lighthouse scores.

Next.js measures the custom font's metrics and generates a second `@font-face` for the system fallback (e.g. Arial) with overrides that make it metrically identical to the custom font:

```css
/* Generated by next/font — you never write this manually */
@font-face {
  font-family: '__Inter_Fallback_abc123';
  src: local('Arial');
  ascent-override: 90.20%;
  descent-override: 22.48%;
  line-gap-override: 0.00%;
  size-adjust: 107.40%;
}
```

The fallback occupies the exact same space as Inter. When Inter loads and the browser swaps, no reflow occurs. CLS is effectively zero.

## CSS variables vs className

`next/font` offers two ways to apply the font:

**className approach:** apply the font directly to one element

```tsx
<html className={inter.className}>
```

The font is applied to `<html>` and inherited by everything. Simple, but the CSS value is embedded in the className — you can't reference it in `.module.css` files without importing the font object.

**variable approach:** inject a CSS custom property

```tsx
export const inter = Inter({
  subsets: ['latin'],
  variable: '--font-inter', // CSS custom property name
});

// In layout.tsx:
<html className={`${inter.variable} ${playfair.variable}`}>
```

```css
/* In globals.css or any .module.css: */
body {
  font-family: var(--font-inter), Arial, sans-serif;
}
h1, h2, h3 {
  font-family: var(--font-playfair), Georgia, serif;
}
```

**Why variable is better for an app-wide font:** the CSS custom property is available to every CSS file without importing the font object there. `globals.css`, any `.module.css`, even inline styles can use `var(--font-inter)`. The className approach requires the font object at every usage site.

## Configuration options

```ts
Inter({
  subsets: ['latin'],    // Only download Latin characters — NOT the full font.
                         // Full Inter is ~1MB. Latin subset is ~100KB.

  variable: '--font-inter', // CSS custom property name

  display: 'swap',       // Show fallback immediately, swap when font is ready.
                         // Alternative: 'optional' — give browser 100ms;
                         // if not loaded, use fallback for the whole page.
                         // 'optional' = zero CLS; 'swap' = near-zero CLS (size-adjust).

  weight: ['400', '700'], // Only for non-variable fonts. Download specific
                           // weights rather than all. Inter is a variable font
                           // (one file covers all weights) — omit this for it.
                           // Playfair Display is not variable — specify weights.
})
```

## The module scope constraint

```ts
// ✓ Correct — at module scope
export const inter = Inter({ subsets: ['latin'], variable: '--font-inter' });

// ✗ Wrong — inside a component
export default function Layout() {
  const inter = Inter({ subsets: ['latin'] }); // silently fails
}
```

Next.js statically analyses font imports at build time to bundle the font files. If the call is inside a function or component, the static analyser cannot find it — the optimisation silently fails, no font files are bundled, and you fall back to a runtime CDN request with no error. Always initialise at the top level of a module.

## Verifying it worked

Open DevTools → Network → Font tab. You should see:

- Font files loaded from `localhost:3000` (or your domain), not `fonts.gstatic.com`
- WOFF2 format (Next.js picks the most efficient format automatically)
- Status 200 with cache headers set

Open DevTools → Elements → `<head>`. You should see:
- A `<style>` tag with the `@font-face` declarations (inline, no external stylesheet)
- The size-adjusted fallback `@font-face` beside the real font declaration
- No `<link>` to `fonts.googleapis.com`
